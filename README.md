# MVSwitcher

MVSwitcher — консольный инструмент для переноса Minecraft-модов между версиями Minecraft (полностью поддержан NeoForge, остальные загрузчики частично: см. «Поддержка загрузчиков»). Он не меняет исходный проект: результат создаётся в отдельном каталоге `converted/` или по пути `--output`.

## Требования и сборка

- JDK 21 (для сборки самого MVSwitcher).
- Gradle 8.10 или новее.
- Для профиля NeoForge 26.3 также нужен JDK 25; для 1.21.11 — JDK 21.

```shell
gradle clean test installDist
```

Запуск:

```shell
build/install/mvswitcher/bin/mvswitcher --help
build/install/mvswitcher/bin/mvswitcher versions
build/install/mvswitcher/bin/mvswitcher interface
```

В Windows используйте `build\install\mvswitcher\bin\mvswitcher.bat`.

### Графический интерфейс и журнал

Команда `mvswitcher interface` открывает Swing-приложение с теми же основными возможностями, что и CLI:

- на вкладке «Миграция» задаются исходная папка/ZIP, исходная и целевая версии, NeoForge, Java, каталог результата, собственные правила, шаблон MDK, `dry-run`, `force` и пропуск сборки;
- анализ проекта запускается отдельно и показывает распознанные метаданные;
- вкладка версий показывает известные профили и направленные маршруты;
- вкладка отчёта содержит итоговый отчёт операции, а общий журнал отображает этапы, срабатывания правил, предупреждения и строки Gradle в реальном времени;
- журнал можно очистить или сохранить в файл. Долгие операции выполняются в фоновом потоке, окно остаётся отзывчивым.

CLI-команды `analyze` и `migrate` также выводят временные отметки и сообщения о стадиях работы; при миграции вывод сборки Gradle передаётся по мере выполнения. Для `interface` требуется графическая среда (оконная сессия).

## Направление и покрытие правил

Направление всегда задаётся как **исходная версия → целевая версия**. В репозитории есть правила для обоих переходов между **26.3** и **1.21.11**. Направление 26.3 → 1.21.11 использует конвертации, проверенные прежним integration workflow; обратные правила инвертируют только изменения, которые были выявлены на исходниках Teromod 1.21.11 и подтверждены его сборкой с NeoForge 26.3.

Это не обещает автоматическую миграцию любого мода: наборы отражают известные изменения API, а итоговая сборка проверяет совместимость конкретного проекта. Пара профилей 1.21.11 / NeoForge 21.11.48 / Java 21 и 26.3 / NeoForge 26.3.0.99 / Java 25 подтверждена; это не доказывает покрытие всех API в каждом моде. Для прочих версий в проекте нет проверенных профилей и наборов преобразований: передавайте параметры NeoForge/Java и добавляйте собственные направленные правила.

Команда `mvswitcher versions` выводит известные профили и имеющиеся в комплекте направленные рёбра. Маршрут из нескольких версий выбирается автоматически только тогда, когда для каждого ребра существует набор правил. Отсутствие маршрута отображается в отчёте; API-совместимость в этом случае не заявляется.

## Получение шаблона и этапы переноса

Для режима с шаблоном сначала получите NeoForge MDK для **целевой** версии — например, через официальный [генератор модов NeoForge](https://neoforged.net/mod-generator/) — и распакуйте ZIP. Выбирайте Minecraft/Gradle-настройки целевой версии. Шаблон можно передать как каталог или ZIP-файл.

```shell
mvswitcher migrate ./MyMod --from 26.3 --to 1.21.11 --template ./NeoForge-MDK
```

В этом режиме конвейер работает в таком порядке:

1. Проверяет исходный мод и целевой NeoForge MDK, включая доступные сведения о версиях.
2. Копирует MDK в выходной каталог и подставляет целевые `minecraft_version`, `neo_version`, `java_version` и существующий `minecraft_version_range`.
3. Собирает чистый MDK. Если эта сборка не проходит, исходные файлы ещё не переносятся, а причина попадает в отчёт.
4. Переносит содержимое исходного проекта поверх шаблона: заменяет примерный `src/`, копирует остальные файлы проекта, кроме Gradle-сборки/обёртки шаблона. `gradle.properties` объединяется: свойства шаблона сохраняются, недостающие добавляются из источника, а значения `mod_*` берутся из исходного проекта. Затем версии Minecraft/NeoForge/Java снова выставляются на целевые.
5. Находит направленный маршрут правил и применяет преобразования в порядке правил каждого ребра.
6. Проверяет синтаксис Java, запускает итоговую сборку и печатает отчёт с изменёнными файлами, количеством срабатываний каждого правила, предупреждениями и выводом обеих сборок.

`--skip-build` пропускает обе сборки (шаблона и результата); он не меняет порядок остальных шагов. Если `--template` не задан, остаётся совместимый прежний режим: исходный проект копируется, затем обновляются известные build-метаданные, применяются правила и запускается итоговая сборка. Этот режим не создаёт новый MDK.

При использовании MDK его `build.gradle`/`settings.gradle`, wrapper и каталог `gradle/` остаются целевыми и не заменяются одноимёнными файлами исходного проекта. Если исходный мод требует особых зависимостей или настроек сборки, перенесите их в целевую конфигурацию и проверьте итоговую сборку; для простых изменений применяйте направленные правила с glob по файлам сборки.

Примеры:

```shell
mvswitcher analyze ./MyMod
mvswitcher migrate ./MyMod.zip --from 26.3 --to 1.21.11 --template ./NeoForge-MDK.zip --dry-run
mvswitcher migrate ./MyMod --from 26.3 --to 1.21.11 --template ./NeoForge-MDK --skip-build
mvswitcher migrate ./MyMod --from 1.21.11 --to 26.3 --neoforge-version 26.3.0.99 --java 25
```

`--dry-run` показывает версии, маршрут и план, не записывая результат. Если выходной каталог уже существует, команда откажется его перезаписывать; для замены укажите `--force`.

При копировании пропускаются каталоги `.git`, `.gradle`, `build`, `converted`, `.idea` и `copilot-worktrees` на любой глубине; также не копируются вложенные Git-репозитории. Это предотвращает попадание рабочих деревьев и сгенерированных исходников в проект переноса.

## Каталог версий

Известные профили (версия Minecraft, загрузчик, версия загрузчика, Java) хранятся данными в `src/main/resources/versions/index.json`, а не в Java-коде:

```json
{ "profiles": [
  { "id": "1.21.11", "minecraft": "1.21.11", "loader": "neoforge", "loaderVersion": "21.11.48", "java": 21 }
] }
```

Чтобы добавить версию, достаточно дописать запись в этот файл. `id` по умолчанию равен `minecraft`, `loaderVersion` можно опустить, тогда его нужно передавать явно.

Необязательное поле `properties` задаёт записи `gradle.properties`, которые нужно выставить при миграции на этот профиль (версии загрузчика, API и т. п.). Для NeoForge `neo_version` берётся из `loaderVersion`, как раньше. Версии, которых вы не знаете наверняка, лучше не вписывать: для неизвестного профиля инструмент оставляет версии загрузчика нетронутыми и пишет об этом предупреждение.

## Поддержка загрузчиков

Загрузчик проекта определяется автоматически: по `neoforge.mods.toml`, `META-INF/mods.toml`, `fabric.mod.json`, `quilt.mod.json`, а если их нет — по Gradle-файлам. Quilt вместе с Fabric-метаданными считается Quilt. Для NeoForge 1.20.1–1.20.4 (где метаданные лежат в `mods.toml`) различие с Forge делается по Gradle. Если в проекте признаки сразу нескольких загрузчиков (multi-loader), он не угадывается, а отклоняется с понятным сообщением: мигрируйте модули по одному.

| Загрузчик | Что делает инструмент |
|---|---|
| NeoForge | Полный конвейер: шаблон MDK, `neo_version`, диапазон версий в `neoforge.mods.toml`, правила, сборка. Есть готовые правила. |
| Forge, Fabric, Quilt | Режим «только правила»: копирует проект, применяет правила своего загрузчика и обновляет в `gradle.properties` только уже существующие ключи (`minecraft_version`, ключи профиля). Готовых правил для них пока нет, их нужно добавлять самим (см. генератор выше). |
| Между загрузчиками | Не поддерживается (Forge → NeoForge, Fabric ↔ Quilt): это не только замена имён, но и другие файлы метаданных, события и регистрация. |

Правило применяется к проектам того загрузчика, который указан в его поле `loader` (по умолчанию `neoforge`). Значение `"*"` означает «любой загрузчик»: оно подходит для правил, которые касаются только ванильного API Minecraft. Существующие правила я автоматически не переводил на `"*"`: правила на имена из Mojang mappings верны для Fabric только если мод тоже использует Mojang mappings (а не Yarn), и это решать вам. Генератору правил `--loader` тоже можно передать `*`.

## Структура и формат правил

Встроенные направленные правила хранятся по пути:

```text
src/main/resources/rules/
  index.json
  <source-version>/
    <target-version>/
      rules.json
```

Например, `rules/1.21.11/26.3/rules.json` — переход с 1.21.11 на 26.3. Каждое правило в файле обязано иметь те же `from` и `to`, что и папки. Для встроенного пакета также добавьте путь файла в `rules/index.json`. Это данные для общего обработчика, поэтому добавление версии/перехода не требует изменения Java-кода.

Минимальный пример пользовательского файла:

```json
{
  "rules": [
    {
      "id": "rename-example-api",
      "from": "1.21.11",
      "to": "26.3",
      "includes": ["**/*.java"],
      "find": "OldApiName",
      "replace": "NewApiName"
    }
  ]
}
```

Поля:

- `id` — уникальный идентификатор правила в загруженном пакете.
- `from`, `to` — исходная и целевая версии для одного направленного шага.
- `includes` — обязательные glob-маски путей относительно корня проекта (`*`, `**`, `?`). Указывайте узкие маски: замена текста не разбирает Java AST и может затронуть комментарии/строки.
- `find`, `replace` — непустой буквальный текст поиска и замена. Пустой `replace` удаляет совпадение. По умолчанию заменяются все совпадения в каждом подходящем текстовом файле.
- Вместо `find` можно задать `findRegex` — регулярное выражение Java. Оно может охватывать пробелы/переносы строк (`\\s*`); в `replace` доступны группы `$1`, `$2` и т. д. Например, правила экранов используют это для сохранения размеров GUI при смене конструктора. Укажите либо `find`, либо `findRegex`, но не оба.
- `maxReplacements` — необязательный положительный предел замен на файл.
- `skipIfContains` — необязательная защита: если файл уже содержит эту строку, данное правило пропускает весь файл; полезно для повторного запуска миграции.
- `required` — необязательный флаг. Если он равен `true`, отсутствие замены по правилу останавливает миграцию с ошибкой. По умолчанию правило может не найти совпадений, что нормально для модов, не использующих соответствующий API.

- `loader` — необязательное имя загрузчика (`neoforge`, `forge`, `fabric`, `quilt`). По умолчанию `neoforge`. Маршрут и применение правил учитывают только правила загрузчика проекта. `id` правил должен быть уникален во всём наборе, независимо от загрузчика.
- `type` — необязательный тип правила: `text` (по умолчанию, меняет файлы) или `warn` (файлы не меняет, только добавляет предупреждение в отчёт).
- `message` — обязательный текст предупреждения для `type: "warn"`. Для таких правил поле `replace` задавать нельзя. Используйте их там, где автоматическая замена небезопасна (смена логики, а не имени), чтобы инструмент указывал файл и количество совпадений, а не молчал.

Пример предупреждающего правила:

```json
{
  "id": "legacy-call-warning",
  "from": "1.21.11",
  "to": "26.3",
  "type": "warn",
  "includes": ["**/*.java"],
  "find": "legacyCall(",
  "message": "legacyCall удалён, перепишите вызов вручную."
}
```

Правила в `rules.json` выполняются сверху вниз. Маршрут между несколькими версиями выбирается поиском кратчайшего пути, при равной длине учитывается порядок рёбер в загруженном наборе. Каждый шаг направленный: обратное правило нужно описать отдельно, а также проверить по API целевой версии.

Функции меняются тем же буквальным механизмом: сузьте `includes` до нужного файла, задайте старую сигнатуру или тело в `find`, а новую — в `replace`. Для многострочного фрагмента используйте `\n` в JSON. Например, правило может заменить `protected int oldSignal(BlockState state) {` на `protected int getSignal(BlockState state, Direction direction) {`. Это намеренно явная текстовая замена, а не автоматическое понимание AST: перед запуском проверьте, что фрагмент достаточно уникален, задав `maxReplacements`.

### Добавление пользовательского правила

Создайте папку правил, например `my-migration-rules/1.21.11/26.3/rules.json`, и передайте корневую папку:

```shell
mvswitcher migrate ./MyMod --from 1.21.11 --to 26.3 --rules ./my-migration-rules --neoforge-version 26.3.0.99 --java 25
```

Каталог правил дополняет встроенные правила; правило с уже существующим `id` заменяет встроенное правило с этим ID, остальные правила добавляются. При передаче `--rules path/to/rules.json` загружается самостоятельный набор правил без встроенных. Проверьте конфигурацию сначала через `--dry-run`, затем изучите секции `Rule applications`, `Warnings`, `Errors` и вывод Gradle в отчёте. Правило, которому нечего заменить, показывает ноль совпадений; `required: true` превращает это в явную ошибку.

## Генератор правил из диффа API

Чтобы не искать изменения API вручную, сравните исходники двух соседних версий Minecraft отдельным инструментом. В `--old` и `--new` можно передать как папку с `.java`-файлами, так и архив `.jar`/`.zip` с исходниками (его не нужно распаковывать). Исходники Minecraft инструмент не скачивает, их нужно получить самим. Обычно они появляются в Gradle-кэше после сборки проекта NeoForge (ищите файлы `*sources*.jar`, например `find ~/.gradle -name '*sources*.jar' | grep -i neoforge`) или в IDE через «Download sources». Исходники Minecraft нельзя выкладывать в репозиторий.

```shell
java -cp "build/install/mvswitcher/lib/*" dev.mvswitcher.tools.ApiDiffGenerator \
  --old ./sources-1.21.11 --new ./sources-26.3 --from 1.21.11 --to 26.3 --out ./generated-rules
```

Результат — `generated-rules/1.21.11/26.3/rules.json` (в формате правил выше, его можно передать через `--rules ./generated-rules`) и `notes.txt` со всем, что не удалось превратить в правило.

Что определяется:

- перенос класса в другой пакет при том же простом имени — правило `text`;
- переименование класса (почти совпадающий набор методов, взаимно лучшее совпадение) — два правила `text`: полное имя и простое имя. Проверяйте их по `notes.txt`;
- переименование метода с той же сигнатурой в том же классе — правило `warn` (замена по одному имени не знает тип получателя). С флагом `--auto-replace-methods` однозначные переименования, где старого имени нет в новом API вообще, превращаются в `text`;
- удалённые классы попадают в `notes.txt`; с флагом `--include-removed` для них добавляются правила `warn` по строке `import`. Таких правил может быть очень много, а движок проходит все файлы для каждого правила, поэтому по умолчанию они выключены.

Это кандидаты на правила, а не готовая миграция: изменения полей, смена порядка аргументов и логики не определяются. Переименование метода после переименования класса сопоставляется по новым именам типов, но сложные цепочки изменений проверяйте вручную. Генератор проверен на синтетических деревьях исходников; на реальных исходниках Minecraft его ещё не запускали.

## Golden-тесты правил

Каждое ребро правил проверяется на примерах кода. Кейс — это папка `src/test/resources/golden/<from>/<to>/<case>/` с двумя подпапками: `input/` (исходники мода в исходной версии) и `expected/` (файлы, какими они должны стать после миграции). Метаданные сборки тест создаёт сам, поэтому в кейсе лежат только исходники. Новый кейс не требует правки Java.

Тест `GoldenMigrationTest` прогоняет все кейсы через настоящий движок (без Gradle-сборки) и сравнивает результат с `expected/` построчно. Второй тест следит, чтобы у каждого ребра из `rules/index.json` был хотя бы один кейс: новое ребро правил без кейса не пройдёт проверку.

## Ограничения

- Полный конвейер есть только для NeoForge. Проекты Forge, Fabric и Quilt проходят в режиме «только правила» (см. «Поддержка загрузчиков»): готовых правил для них нет, режим ни разу не запускался на реальных проектах этих загрузчиков, только на тестовых. Миграция между загрузчиками и multi-loader проекты не поддерживаются.
- Встроенные профили сейчас есть только для 1.21.11 / NeoForge 21.11.48 / Java 21 и 26.3 / NeoForge 26.3.0.99 / Java 25.
- Встроенные API-правила есть для 26.3 → 1.21.11 и 1.21.11 → 26.3, но обратный набор ограничен конкретными различиями, проверенными на Teromod. Для других модов изучайте ошибки сборки и добавляйте точечные правила; профиль версии и запуск сборки не означают полной совместимости.
- Успешная сборка не проверяет поведение мода в игре. Проверяйте мигрированный проект и тестируйте его отдельно.
- Шаблон заготавливается отдельно официальным NeoForge-генератором и передаётся через `--template`; инструмент проверяет и собирает его, но не загружает MDK сам.
